# زاد (was «عمار») — PWA source, v4.0 … v5.4.7

Live: https://zad.sites.tab.bot/ (site `zad`, proxy → amar-muslim) and https://amar-muslim.sites.tab.bot/ (site name `amar-muslim`, the real Worker + D1/R2; APK bound here)

## Adding a changelog entry on every future update (3 edits)
1. `src/up-src.js`: add a new entry at the TOP of `CL`, e.g.
   `['3.9','٢٥ أكتوبر ٢٠٢٦',['ميزة جديدة …','تحسين …']],`
   and set `var APP_VERSION='3.9';` (the same number).
2. `site/sw.js`: bump `const V='ammar-v3-9';`. A new cache name is what makes phones see the update.
3. Minify: `npx terser src/up-src.js -c -m -o site/up.js`, then publish.

What users see next: their app finds the new service worker (on open, every 30 min, and when the app comes back to the foreground) → banner «🎉 تحديث جديد متوفر» + «حدّث الآن» (calls skipWaiting, then reloads) → after reload the «ما الجديد» popup shows CL[0] once (localStorage `ammar.lastSeen` ≠ APP_VERSION). If notifications are allowed, the SW also fires «تحديث جديد لتطبيق زاد — اضغط لتشوف الجديد» on activation, which opens #whatsnew.
A fresh install (not onboarded yet) never gets the popup: lastSeen is set silently. Existing users from before v3.8 (onboarded, no lastSeen key) do get it once.
Full history page: route `#whatsnew` (also linked from Settings and app search).

## App name
The name is one value: `var APP_NAME="…"` at the top of `site/index.html`. All JS (watermarks, share texts, canvases, onboarding) reads it.
To rename everything (title, apple title, header, manifest, SW notification, credits) run:
`node set-name.mjs "الاسم" site`

## Publishing
The stock CLI switches to a multi-request "staged" upload above 1,300,000 bytes, and that path currently fails on the control side (ENOENT index.html). `pub1.mjs` sends the whole folder in ONE request through the same capability (fine up to ~1.45 MB raw, under the gateway's 2,000,000-byte request bound):
`node pub1.mjs site amar-muslim "زاد — تطبيق المسلم"`

## v4.1 (24 Oct 2026) — closed-app reminders (Web Push)
- Server: `srv/worker-src.js` + `srv/legacy.js` (the v4.0.1 worker: assetlinks, /install, /book/raheeq.pdf, unchanged) + `srv/adhan-umd.js` (same adhan-js file as site/adhan.js) → `sh srv/build-worker.sh` writes `site/_worker.js`. `/api/push/*` is handled first; everything else goes to the legacy worker, so `/.well-known/assetlinks.json` stays byte-identical.
- Prayer times on the server are an exact port of `src/pt-src.js` (same adhan-js, method ids, Ramadan isha 120, Asr refinement, minute rounding, tune). Checked: 125 times across 5 time zones identical to the app's on-device function.
- `site/tab-site.json` binds a D1 database `DB` (additive tables `push_subs`, `push_sent`, `push_meta`, created with IF NOT EXISTS on first call).
- VAPID: the key pair is generated ONCE by the server itself (WebCrypto ECDSA P-256) and stored in D1 `push_meta.vapid`. The private key never leaves the server and never appears in the source or logs. `GET /api/push/key` gives the public key.
- Endpoints: `POST /api/push/subscribe|update` {sub, lat, lng, city, tz, cfg}, `POST /api/push/unsubscribe` {endpoint}, `POST /api/push/test` {endpoint} (30 s rate limit), `POST /api/push/kick` (any open app nudges a tick if none ran for 150 s — backup for the cron).
  Token-protected (`?k=`, `Authorization: Bearer` or `X-Tick-Token`; only the SHA-256 of the token is in the code): `/api/push/tick`, `/status`, `/preview`, `/peek`, `/force`.
- Scheduler: cron-job.org free account (email amar.alshammari@mail.tab.bot; password, API key and tick token are in Tab's vault: `item:cron-job.org password (amar.alshammari@mail.tab.bot)`, `item:cron-job.org API key`, `item:zad push tick token`). One job, every minute, GET https://amar-muslim.sites.tab.bot/api/push/tick with header X-Tick-Token.
- Tick: claims due rows atomically (`UPDATE … RETURNING`, index on next_at), 50 per batch, up to 10 batches / 20 s per tick, 8 sends in parallel. Sent-log `push_sent` keyed `sub|event|local-date` (INSERT OR IGNORE) → never twice. 404/410 (and Apple BadWebPushToken) delete the subscription; 429/5xx retry next tick inside the grace window. Each row stores its next event (`next_at`), so a tick only touches who is due. More capacity = add a 2nd cron job (claims are atomic).
- Events per user (same rules as the app): adhan per prayer (adhan-js, same method id + per-prayer tune as Settings), أذكار الصباح = Fajr+20 min, المساء = Asr+20 min, fasting eve at `Z.fast.time` when tomorrow is Mon/Thu/White Day (Umm al-Qura via Intl, ±adj, no Ramadan / 1 Shawwal / 10–13 Dhul-Hijja), suhoor at `Z.fast.stime` on the fasting day, Kahf Friday 09:00, sadaqah weekly. Grace windows: adhan 15 min, suhoor 45 min, others 1.5–3 h (a missed tick never sends a stale adhan).
- Client: `src/zpush-src.js` → `site/zpush.js` (`npx terser … -c -m`). Route `#push`; entries in Settings, the hub, a dismissible home nudge and the #sawm page. iPhone not installed → home-screen guide; iOS < 16.4 → explanation. When push is on, the in-app timers keep the bell log/toast but don't show a 2nd notification, and the SW periodic-sync fallback stands down (cache flag `/__zadpush`).
- SW: `push` handler (Arabic title/body, icon, tag, tap opens the screen via `data.url`) + `pushsubscriptionchange` re-subscribe.

## v4.4.2 (24 Oct 2026) — faster, cleaner video player + «تحميل»
عمار (12:55/12:57 PM): «حسن المشغل وخلي المقاطع تنزل» / «في بطء وتشغيل بدائي وايقونات خايسة / لا تخصص ايقونة لعمار خليها مع المقاطع».
- **Diagnosis (live v4.4.1):** the server was fine (206 Range, Accept-Ranges, video/mp4, ~0.3 s first byte, SW passes /api/ through) and the 3 episodes were already faststart. The slowness was size + client: 1080×1920 High@4.0 files (4.1–5.3 MB) and the old feed started the current AND next clip at the same moment and fetched every poster (97–143 KB each) up front, so on a 1.5 Mbps line the first frame took ~4.2 s. The error handler crashed on official clips (no `.zv-exp`), so a failed load showed nothing.
